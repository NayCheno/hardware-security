研究背景：Web Fuzzing 缺少可信基准
➢ Web fuzzing 工具长期缺乏统一可靠的 benchmark
➢ 现有评测方式存在明显偏差：
1. 教学靶场

--- Page 199 ---
防御维度1：建立接口与参数资产清单
1. 统一接口注册
• 所有 Web handler、CGI、Lua handler、REST API 都必须进
入中心注册表
• 每个接口明确声明 URI、Method、认证要求、权限等级、
参数列表
• 未注册接口不得进入发布固件
2. URI-Key 规格化管理
• 为每个参数定义类型、长度、范围、枚举值、编码格式
• 参数规格同时用于前端页面、后端校验、测试用例生成
3. 输入源点显式标注
• 对 websGetVar、getenv、cJSON_GetObjectItem、Lua table 访
问等输入函数做统一封装
• 标注哪些 Source 来自外部用户，哪些来自系统内部
• 对用户可控 Source 默认施加强校验
4. 发布前检查
• 比对前端提取的参数、后端实际解析的参数、接口注册表
• 发现“后端存在但前端无入口”的参数时，强制进入安全审
查
Source不应让攻击者从二进制中逆向发现，而应该成为厂商可管理、可审计的资产
199

--- Page 200 ---
防御维度2：跨组件数据流建立安全边界
1. 对 IPC 数据键做分级
• NVRAM key、环境变量、临时文件路径、Socket 
消息字段都应纳入数据资产
• 标注哪些 key 可能被 Web 请求间接控制
• 高风险 key 禁止直接进入命令执行等危险函数
2. Setter / Getter 双向约束
• Setter 写入前做格式化和净化
• Getter 读取后仍要重新验证，不能默认信任存储层
数据
• 对跨进程传播的数据保留“用户可控”语义
3. 跨语言调用边界防护
• Lua 调 C、C 调 Lua、脚本调用二进制时，必须明确参数 schema
• 禁止 Lua 中拼接命令后直接传给 C 二进制或系统命令
• 对 os.execute、forkExec、system 等接口建立安全包装层
4. 组件最小权限
• Web 服务进程、配置服务、系统命令执行服务分离权限
• 低权限 Web 组件不应直接修改系统级配置
• 高危操作通过受控 API 完成，而不是通过 shell 字符串拼接
在每一次跨边界数据传输过程中均设立安全约束，防止恶意数据流动

防御维度3：隐藏接口治理与认证
1. 消除未注册路由 Token
• 所有 action、cmd、op、method、service name 
等路由 Token 必须登记
• 构建阶段扫描二进制和脚本中的 Token
• 发现注册表之外的 Token，直接阻断发布
2. 调试接口发布门禁
• test、debug、diagnostic、factory、dev、backup 
等接口不得进入正式版本
• 必须保留的诊断接口应绑定认证、权限、审计
日志和访问来源限制
3. 隐藏接口统一认证
• 路由分发前先做认证和授权，而不是进入 handler 
后再判断
• 敏感操作必须验证角色权限和 CSRF 防护
4. 降低自动化枚举价值
• 未授权、参数错误、不存在接口返回一致化响应
• 不在响应中泄露内部路径、函数名、固件版本、
调试信息
• 对大量路径探测、Token 枚举、异常参数组合做速
率限制和告警
攻击者利用路由Token推断隐藏接口；厂商可反向使用Token扫描消除未登记入口

防御维度4：用“约束一致性”主动式发现漏洞
1. 三类约束统一建模
• 前端显式约束：maxlength、正则校验、下拉枚举、JS 检查等
• 后端显式约束：长度检查、字符过滤、路径规范化、权限判断等
• Sink 期望约束：缓冲区容量、命令参数字符集、文件路径边界等
2. 识别约束不一致
• 前端限制长度，但后端未限制 → 高风险
• 后端检查长度，但未检查命令分隔符 → 命令注入风险
• Sink 需要固定大小缓冲区，但 Source 可传入超长数据 → 溢出风险
• 前端隐藏参数，但后端仍可解析 → 隐藏输入风险
3. 自动生成验证用例
• 从 URI-Key 清单生成合法请求骨架
• 从 Source-Sink 路径提取关键参数
• 从约束缺口生成漏洞验证用例
4. 修复后回归
• 每个已确认漏洞转化为回归测试
• 后续固件版本必须重复验证同一路径
• 防止补丁只修前端、不修后端
将“漏洞验证能力”前移到发布前，而不是等漏洞被披露后再采取缓解措施

其他缓解措施：默认配置安全
1. 默认关闭 WAN 侧管理入口
2. 管理面仅允许 LAN、VPN 或可信管理通道访问
3. 禁止默认弱口令，每台设备使用唯一初始凭据
4. 对接口枚举、爆破、异常参数组合做限速和告警
5. 所有敏感接口必须有认证、授权、日志和速率限制

缓解措施总结：建立内部安全流水线
1. 固件解包与资产提取
1. 提取 HTML / JS / Lua / PHP / CGI / ELF / shared library
2. 生成 URI、Key、Token、NVRAM key、Sink 函数清单

1. 前后端关键词匹配、URI-Key 结构化恢复
2. LLM 辅助判断输入处理函数语义
3. Propagation 追踪
1. 分析 NVRAM、环境变量、文件、Socket 等 IPC
2. 建立跨二进制依赖图
3. 建立 C-Lua / 脚本-二进制跨语言数据流
4. Hidden Interface 检测
• 从文件系统和二进制中提取路径和路由 Token
• 对未登记接口做黑盒探测，恢复隐藏接口的参数规格
5. Sink 与约束分析
• 检查 system、popen、execve等危险操作
• 比对前端约束、后端约束和 Sink 期望约束
• 输出高置信漏洞候选
6. 动态验证与回归
• 根据 URI-Key 和 Token 字典生成 Fuzzing 请求
• 在真实设备或仿真环境中验证可达性
