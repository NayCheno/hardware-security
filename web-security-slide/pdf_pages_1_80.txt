背景 - 网络设备Web接口安全与技术瓶颈
• 首要攻击面： 物联网（IoT）及网络设备的Web接口（如路由器管理面板）是对外暴露的主要通
信接口，极易成为命令注入、缓冲区溢出等污点型漏洞的攻击目标
• 传统分析工具（静态分析/Fuzzing）在IoT Web固件上面临四大挑战：
1. 入口识别难：缺乏源码，传统工具难以定位后端二进制程序真实的污点源
2. 数据流极其复杂：现代固件高度解耦，数据流常因多进程通信（如NVRAM、环境变量）或多语言混
合架构（C与Lua等脚本交互）而截断
3. 隐藏接口泛滥：厂商遗留的测试接口缺乏前端入口且无认证保护，传统爬虫无法触达，成为严重后门
4. 漏洞验证困难：纯静态分析告警海量且误报极高；而动态Fuzzing由于硬件依赖难以运行固件，且在黑
盒设备上缺乏代码覆盖率反馈

维度一：输入源点识别 (Source)
• 核心痛点： 在后端二进制中盲目寻找输入点 (Source) 会引入大量无效路径与误报
• 技术演进逻辑（从盲找到语义协同）：
1. 基石（关键字匹配）：首次提出利用前端（HTML/JS）与后端共享的“关键字”作为Oracle，定位后
端输入点【SaTC, USENIX Security 2021】
2. 演进1（模糊匹配）：解决硬编码与格式差异导致的漏报，引入基于编辑距离与自然语言处理
（NLP）的模糊匹配与语义相似度计算【HermeScan, NDSS 2024】
3. 演进2（结构化建模+LLM）： 单纯匹配关键字依然受限，将输入结构化为URI和Key（键）的映
射，并利用大语言模型（LLM）理解代码上下文，剔除误报【LARA, USENIX Security 2024】

研究背景
➢IoT 路由器、摄像头等设备普遍暴露 Web 管理服务
• 攻击者可以通过 HTTP 参数触发后端二进制中的危险操作

• 动态执行/仿真覆盖率低且依赖硬件环境
• 传统静态分析又难以识别前后端交互中的真实用户输入
➢关键瓶颈
• 如果不知道后端哪里真正读取了 Web 输入，后续污点分析会在无关路径上浪费大量时间

核心洞察
• 物联网设备通常包含Web管理界面（前端）和二进制服务程序（后端）
• 共享关键词 (Shared Keywords): 前端用于构建请求的参数名（如 "username", "passwd"），通常
以字符串常量的形式直接出现在后端二进制中，用于解析数据
→ 不去模拟整个系统，而是利用这些“关键词”作为锚点，直接定位后端处理用户输入的代码区域

核心方法一：前端关键词提取
• 输入: 固件解压后的文件系统
• 处理:
1. 解析 HTML, JavaScript, Lua, PHP 文件
2. 识别 <input>, <select>, textarea 等标签
3. 识别 XMLHttpRequest, fetch 等API调用
• 建立停用词表 (Stoplist)，剔除 CSS 类名、DOM ID、常见 UI 词汇 ("submit", "cancel", "width")
• 输出: 候选关键词列表
• <input name="X">, <select name="X">  → 提取 X
• param = "user=" + v1 + "&pwd=" + v2 → 提取 "user", "pwd"
• "key": value → 提取 "key" 9

--- Page 10 ---
核心方法二：后端参考点定位
• 目标: 关注数据提取函数 (Data Retrieval Functions, DRFs): 
• 例如: http_get_param, cJSON_GetObjectItem, getenv
• 算法: 如果一个关键词作为参数传递给了疑似DRF的函数，则该位置被标记为入口点
1. Candidate Selection: 收集所有接受前端搜集到的关键词作为参数的函数
2. Clustering: 如果该函数在不同调用点接受了多个不同的前端关键词 (e.g., "username", 
"password", "ip")，则该函数的候选分数 Score 增加
3. Data Flow Check: 检查该函数的返回值是否被后续指令使用 (Live Variable)
4. Threshold: 选取 Top-N Score 的函数作为 DRF
10

--- Page 11 ---
核心方法三：污点分析技术
• 污点源建模 (Source Modeling)
1. Explicit Source: DRF 函数的返回值
2. Implicit Source: 某些函数通过输出参数返回数据，需识别指针类型的参数作为 Source
• 例如：json_get_value(obj, "key", &out_buf)
• Taint Tagging: 为每个 Source 分配唯一的 Tag，以便后续区分不同输入源
• 汇聚点与危险操作建模 (Sink Modeling) 
1. Command Injection: system, popen, execve
• 漏洞模式：污点数据作为命令字符串的一部分，且未被引号包裹或转义
2. Buffer Overflow: strcpy, strcat, sprintf
• 漏洞模式：污点源作为 Source Buffer，且未进行长度检查

--- Page 19 ---
核心洞察
➢ Insight 1：将污点追踪降维为“数据可达性”问题 (Lightweight RDA)
• 不需要沉重的符号执行来求解每一条路径的约束，污点追踪的本质只是判断“源点的数据能否到达 Sink 点”
• 通过引入编译原理中轻量级的可达定义分析 (Reaching Definition Analysis, RDA)，高效遍历所有语句
➢ Insight 2：重建跨越边界的代码图谱 (Enhanced CFG)
• 有了轻量级的 RDA 作为底座，我们可以轻量级扩展到外部库分析
• 通过分析库依赖关系，将二进制主程序的 CFG (Bin-CFG) 与共享库的 CFG (Lib-CFG) 打通，找回丢失的 Sink 点
➢ Insight 3：从“硬编码匹配”走向“语义容错” (Fuzzy Matching)
• 前后端的关键字匹配容易因细微差别就匹配失败 (例如: username vs. user_name)
• 引入基于自然语言处理（如 BERT）的模糊匹配与语义相似度推断，找回非标准的隐藏 Source 点
把“路径能否被求解”转化为“定义是否能到达危险使用点”，保留漏洞追踪能力，同时显著
降低大规模固件分析成本 19

--- Page 21 ---
关键技术 1 - 增强的 CFG 恢复
1. 函数边界识别: 
• 扫描汇编代码特征 (如 Prologue)，补充反汇编工具遗漏的函数
2. 符号名恢复: 
• 即使 Section Header 被剥离 (Stripped)，也通过解析 ELF 的 Program Header 和 PT_DYNAMIC 段
来恢复符号表
3. 调用约定 (Calling Convention) 恢复: 
• 恢复参数传递规则 (如 MIPS 下的 a0-a3)，确保数据流分析的连贯性
4. 库连接: 
• 建立共享库的 CFG (Lib-CFG) 并将其与主程序 CFG 连接，解决跨库分析问题
21

--- Page 22 ---
关键技术 2 - 源输入识别 (模糊匹配)
• 问题: 
• 前端 (Web文件) 和后端 (二进制) 共享的关键词可能存在形态或语义上的差异，精确匹配会漏报
• 解决方案: 双重模糊匹配策略
1. 字面相似度 (Format Similarity): 使用归一化的 Levenshtein 编辑距离
• 例子: 前端 hostname_1.1 vs 后端 hostname_%s
2. 语义相似度 (Semantic Similarity): 使用预训练模型 BERT 计算 Embedding 的余弦相似度
• 例子: 前端 banned for security 与后端 sec_ip_ban 建立语义关联
22

--- Page 23 ---
关键技术 2 - 源输入识别 (候选检查)
• 候选函数检查: 
• 并非所有引用共享字符串的函数都是输入函数
• 算法: 对候选函数进行 Def-Use 分析
• 检查参数: 参数指向的内存是否被存入 (Stored) 数据？如果是，标记为污点源
• 检查返回值: 返回值是否被后续操作使用 (Used)？如果是，标记为污点源
• 约束推断 (Constraint Inference): 
• 利用值集分析(VSA, Value Set Analysis) 推断输入长度约束 (例如 strncpy 的长度参数)
• 避免无限制的符号变量导致的误报
23

--- Page 24 ---
关键技术 3 - LCO 跨过程分析
1. 轻量级 (Lightweight): 
• 使用 RDA (基于 VEX IR) 替代符号执行，无需遍历所有分支，避免状态爆炸
2. 上下文敏感 (Context-sensitive): 
• 在函数调用时传递变量定义，处理别名 (Aliasing) 问题
3. 按需分析 (On-demand):
• 仅当函数参数被标记为污点时，才进入该函数分析
• 对常见 Libc 函数 (如 strcpy, sprintf) 使用摘要 (Summary)，对其他库函数则跟进分析
24

关键技术 3 - 路径合并策略
• 问题: 
• 污点分析通常面临路径爆炸，尤其是存在多个源和汇时

--- Page 32 ---
研究背景
1. 精确匹配的缺陷
• 现有技术高度依赖前端文件与后端二进制文件中“关键字”的精确匹配来定位污点源
2. 隐藏输入（Hidden Inputs）的漏报
• 由于前端文件并未包含所有用户输入逻辑，许多后端处理的“隐藏参数”缺乏前端映射，
现有工具因无法匹配此类关键字而产生大量漏报
3. 缺乏语义理解导致的误报
• 传统的模式匹配无法理解代码上下文语义，只要函数参数中包含类似关键字的字符串
（如 PWD_password），即可能被错误标记为输入处理函数，从而引发误报

--- Page 33 ---
核心洞察
➢Insight 1：用户输入的结构化分类（“URI-Key”二元结构）
• 用户输入通常以表单（Forms）形式组织，具有明显的层级结构

关键模块2：二进制依赖图构建（下）
➢ 设计目标：重构多组件环境下的全局数据流拓扑
➢ 基于 CPFs 收集的通信端点与数据键，KARONTE 构建了一个有向图
➢ 二进制依赖图（Binary Dependency Graph, BDG）
1. 图的定义：G=(B,E); 其中节点 B 代表处理受控数据的二进制文件集合
2. 有向边属性：边 E 由一个三元组表征，包含源节点属性、目标节点属性以及关联的数据键 k
3. 连接逻辑：如果二进制文件 b1 在某处作为 Setter（如调用 setenv 设置了键 k），而 b2 作为
Getter（如调用 getenv 获取了键 k），则在 BDG 中生成一条从 b1 指向 b2 的有向边
➢ 作用：BDG 精确描绘了污染数据如何跨越进程边界传播，为后续全局污点跟踪提供了导航路径

➢KARONTE 基于 BDG (Binary Dependency Graph)对固件执行深度的静态污点传播与符号路径探索

核心洞察
➢ Insight 1：边界二进制过滤会带来系统性漏报
• KARONTE、SaTC 为了提升可扩展性，只分析少量 Border Binaries，但真实固件中的漏洞可能位于内部服务、辅助程序或后
利用链路中；因此 MangoDFA 认为应覆盖固件中的所有相关二进制，而不是只看外部入口程序
➢ Insight 2：污点型漏洞不能只看“是否到达 Sink”
• 传统布尔污点只能判断输入是否传播到 system、strcpy 等危险函数，却无法区分输入是否经过 atoi、格式化、长度限制或常
量替换等安全转换；MangoDFA 因此用 Rich Expression 记录值的来源、类型和历史操作
➢ Insight 3：从 Sink 反向追踪比从 Source 正向传播更适合大规模固件分析
• 固件中的输入源数量庞大，正向追踪会探索大量无关路径；MangoDFA 从危险 Sink 出发反向查找可控 Source，只分析与危
险调用直接相关的数据流，并在遇到常量、安全值或不可利用转换时快速剪枝
➢ Insight 4：跨二进制传播可以通过环境变量 / NVRAM 的 Setter-Getter 关系轻量拼接
• 很多固件漏洞跨进程传播，但不一定需要重型符号执行；MangoDFA 预先构建环境变量和 NVRAM 的读写字典，在分析时直
接连接跨二进制数据流，从而兼顾覆盖率和效率
追求全固件覆盖和可扩展性，用 Sink-to-Source + 富表达式把搜索空间控制在危险数据流附近

➢ 设计目标：规避路径爆炸的黑盒化调用处理

研究背景：符号执行的性能瓶颈与“过度污点化”
1. 动态符号执行的性能瓶颈
• 传统工具（如 SaTC）从源点 (Source) 向汇聚点 (Sink) 进行前向符号执行，试图穷举所有执行路径

• 包括自建最新固件集（160个）、SaTC 基准集
• 包含 1542 个固件的大规模在野数据集，涵盖主流路由器及工业物联网设备
➢0-Day 漏洞发现
• 在最新固件集中精准过滤出 109 个高危警告
• 人工验证了 49 个 0-Day 漏洞（含 7 个直接漏洞与多起跨进程传递性漏洞）
➢ 对比评估

• 对比 MangoDFA (细粒度精度优势)：同为基于 RDA 的工具，MangoDFA 在面对复杂间接调用（如 Cisco 固
件）和参数极多（超出寄存器数量）的格式化函数时表现不佳，召回率仅 16%，而 OctopusTaint 凭借 AIL 
优化和稳健的底层修复，召回率高达 83% 80
